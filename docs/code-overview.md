# Code Overview

Last updated: 2026-06-26

## Application Entry

- `backend/app/main.py` creates the FastAPI app, initializes the runtime schema on startup, mounts `/static`, and serves the browser UI at `/`, `/config`, `/zotero`, `/literature`, `/ontology`, `/prompts`, `/suggestions`, `/curation`, and `/export`; `/curation-prompt`, `/curate-prompts`, `/ontology-suggestions`, and `/evaluation` remain compatibility paths to the static app and map client-side to Prompts or Suggestions.
- `backend/app/api/routes.py` contains the JSON API used by the browser UI.
- `backend/app/ontology_suggestions.py` implements the read-only ontology suggestions workflow: Markdown/YAML-front-matter prompt-template storage, project literature/ontology context selection, cheap dummy LLM tests, strict JSON validation, prompt template title/version run metadata, run-file logging under `data/ontology_suggestions`, cost estimation, and accepted-suggestion handoff into the candidate queue.
- `backend/app/ontology_suggestion_diagnostics.py` implements provider connectivity diagnostics and log writing under `data/ontology_suggestions/logs/api_function_tests/`; the real LLM pipeline test logs live under `data/ontology_suggestions/logs/llm_pipeline_tests/`.
- `backend/app/static/index.html`, `styles.css`, and `app.js` implement the dependency-light browser workflow.
- `backend/app/projects.py` contains the shared project workflow service layer: project folder creation, active project selection, curation-run creation, suggestion parsing, review storage, metric computation, run comparison, project TSV export, and ODK operation logging.
- The static UI includes a fixed shared top-bar logo, persistent active-project banner, dashboard project hierarchy tree, local-storage-backed theme selection, client-side route handling for header/dashboard links, page-scoped startup loading with visible startup/page errors, accessible click acknowledgement toasts, long-running button busy states, provider/model LLM configuration with connection testing, Docker/ODK diagnostics, a single Prompts prompt-library page, a combined Suggestions page with Run, Review, and Evaluation panels, template selection, prompt preview/editing, LLM pipeline test, provider connectivity diagnostics, cost preview, selected literature scope, selected ontology context mode, focused top-down SVG ontology browser rendering, candidate rejection controls, and saved API configuration selection.
- The static UI also includes project management, structured suggestion review, and evaluation pages at `/projects`, `/suggestions`, and `/evaluation`.
- `zotero_lit_md/` is a standalone CLI package exposed through `python -m zotero_lit_md`; it reads Zotero Desktop's local API for parent and child attachment keys, discovers stored PDFs from local Zotero storage folders on disk, extracts PDF text, and writes one LLM/RAG-ready Markdown file per PDF.
- `Dockerfile`, `docker-compose.yml`, and `.dockerignore` define the container runtime. The image installs the app, static UI, Python dependencies, Java, `make`, `git`, and a ROBOT wrapper; Compose mounts persistent `/data`, `/ontology`, and `/odk` paths.

## Configuration Flow

- `backend/app/config.py` defines environment-backed settings with the `OCA_` prefix.
- `backend/app/services/runtime_config.py` overlays browser-saved settings from the `app_settings` table and masks secrets in API responses.
- Browser configuration endpoints save Zotero, provider-neutral LLM settings, local ontology path, and the Zotero literature source path without returning API keys in clear text. LLM provider input is normalized to canonical provider keys before saving and before activating saved LLM configurations.
- The Zotero Metadata Sync form uses stable input IDs in the static HTML. `backend/app/static/app.js` binds the Zotero save/test/sync handlers in `bindZoteroMetadataSync()` after DOM readiness, reports missing required Zotero panel elements through `#zotero-message` and the app status, and guards optional controls before nested selector access.
- LLM provider metadata comes from `backend/app/llm/presets.py` through `GET /api/config/llm/providers`. Presets define provider label, default model, model list, default base URL where applicable, expected API key environment variables, timeout, retry count, temperature, and max output tokens. `POST /api/config/llm/test` uses the active runtime config and returns provider, canonical `provider_key`, model, key presence/source, latency, status, and a short response/error.
- `GET /api/diagnostics/docker-odk` reports mounted literature/ontology/ODK paths plus ROBOT, Java, make, and git availability.
- Settings owns Zotero/local literature paths and masked publisher/source API settings for Elsevier, Springer, Wiley, Crossref, NCBI, and OpenAlex. Literature owns one import action, staged review/edit/promotion, curated editing/project tags, and confirmed unpromoted cleanup.
- The legacy curation prompt API remains available through `/api/curation/prompt`, but the visible prompt-management navigation is consolidated under Prompts. `/api/curation/suggestions/run` still uses the saved curation prompt with the selected Existing Ontology `.obo` file and `combined_literature.md`.
- Saved API configurations are persisted as secret-masked server-side entries in `app_settings`, with active Zotero/LLM/publisher configuration IDs.

## Project Flow

- `backend/app/models/db.py` defines project-oriented tables: `Project`, `CurationRun`, `Suggestion`, `ReviewDecision`, `EvaluationMetric`, and `OdkOperationLog`.
- Existing `LiteratureDocument`, `LiteratureSource`, `ExtractionRun`, `CandidateTermRecord`, and `LiteratureIndexEntry` records now include nullable `project_id` columns so current databases can be upgraded without deleting legacy global workflow data.
- `backend/app/db/session.py` continues to provide SQLite-compatible runtime schema upgrades until formal migrations exist.
- `backend/app/projects.py` creates the requested project folder layout under `projects/<project_slug>/`, writes `project.json`, stores active project state in the `projects.active` flag, validates project metadata, resolves parent/child hierarchy, suggests base IRIs, counts project-tagged literature, and computes optional path statuses.
- Project API routes in `backend/app/api/routes.py` expose creation, selection/activation, children listing, metadata update/readout, project ODK validation/logging, and accepted-suggestion TSV export.
- The browser Projects page calls `/api/projects`, `POST /api/projects`, `PATCH /api/projects/{project_ref}`, `POST /api/projects/{project_ref}/select`, and `GET /api/projects/{project_ref}/children` indirectly through project payloads.
- `backend/app/static/index.html` and `backend/app/static/app.js` implement visible project-management scaffolding: wizard steps, optional AI metadata draft button, project type selector including `existing_ontology_project`, parent-project selector, short description/minimal scope fields, optional workspace/ontology/literature/Git path fields, project cards, selected-project detail/next-step panel, edit metadata mode, active-project selection, hierarchy display, path-status cards, failed-save form preservation, structured project error messages, and empty-field-only AI metadata filling. The same static UI keeps the Literature page split into mutually exclusive `Curated Literature` and `New / Uncurated Literature` sub-tabs with tab-local search/status filters plus shared canonical project-tag filters.
- The Dashboard renders active project name, type, ontology ID/prefix, parent, child projects, workspace/repository metadata, tagged-literature count, optional path statuses, and a nested project hierarchy tree after `/api/projects` loads. Project tiles can set the active project, link to project details/editing, and create child projects. This display does not make literature, graph, candidates, or exports fully project-aware yet.
- Each project exposes one canonical project tag, currently the project `ontology_id`. Literature entries still store a JSON list because one entry can belong to multiple projects; slug/id/name aliases are normalized to canonical tags and preserved as legacy metadata when encountered. Legacy Zotero source tags remain supported independently.
- The CLI exposes the same flow through `oca project create`, `oca project list`, `oca project select`, and `oca project show`.

## Project Curation And Evaluation Flow

- Prompt strategies are defined in `backend/app/projects.py` as `literature_only`, `ontology_only`, `literature_plus_ontology`, and `structured_relation_extraction`.
- `POST /api/curation/runs` creates a project-scoped `CurationRun`; if raw LLM JSON is supplied, `persist_suggestions()` parses a top-level `suggestions` array into `Suggestion` rows while preserving raw output and returning warnings for malformed JSON.
- `GET /api/suggestions` lists suggestions for the active or requested project, optionally filtered by run, review status, suggestion type, and evidence availability.
- `POST /api/suggestions/{suggestion_id}/review` stores a persistent `ReviewDecision` with one of `accepted`, `edited`, `rejected`, `duplicate`, `unsupported`, or `further_review`.
- `POST /api/evaluation/compute` calculates review/evidence metrics from stored rows and writes reproducible `EvaluationMetric` records.
- `POST /api/evaluation/compare` compares two runs with exact label overlap, normalized label overlap, and relation triple overlap.
- `GET /api/projects/{project_ref}/exports/accepted.robot.tsv` exports accepted/edited project suggestions by default, excluding rejected, duplicate, unsupported, and further_review suggestions.
- CLI equivalents live under `oca curation ...`, `oca evaluation ...`, and `oca ontology export-templates`.
- The separate ontology-suggestions CLI group lives under `oca suggestions ...` and exposes `prompts`, `test`, `test-api`, `run`, `list-runs`, and `show-run`. Cheap tests use dummy literature/ontology context and real runs require an explicit literature item.

## Zotero Flow

- `backend/app/zotero/client.py` wraps the Zotero Web API and follows pagination through Link headers.
- The Zotero client can fetch all items, one parent item, and child attachment items through the configured user or group library endpoint.
- The same Zotero client supports Zotero Desktop's local API when configured with base URL `http://127.0.0.1:23119/api`, library type `user`, library ID `0`, and an empty API key. Request headers always include `Zotero-API-Version: 3`; `Zotero-API-Key` is omitted when no key is configured.
- `backend/app/zotero/importer.py` normalizes Zotero API or CSL-like records into `LiteratureSource` rows.
- `POST /api/zotero/sync` defaults to no limit, imports Zotero metadata rows, compares Zotero identifiers against staged and curated local literature, and only sends new entries into the canonical import path. Stable comparison uses DOI, PII, PMID/PMCID, arXiv, ISBN, ISSN+title, URL, then normalized title+year.
- `GET /api/zotero/entries` feeds the dedicated Literature/Zotero page. Entry payloads include a Zotero select URI only when the provider item key is valid and unambiguous, and the frontend renders title-first records with metadata and expandable per-record Markdown. Repository-only Markdown records created by the integrated PDF pipeline are appended so PDF imports are visible even without matching Zotero metadata rows.
- `backend/app/literature/exporter.py` builds an initial LLM-ready literature export from the runtime SQLite cache and creates the `literature/` folder automatically.
- `backend/app/literature/repository.py` manages the per-paper LLM-ready Markdown repository. It can reset the repository recursively, clear stale sidecars, write one `.md` file per paper with canonical YAML/provenance/review front matter, load valid and usable `ready_for_llm` Markdown files recursively while skipping malformed, blocked, incomplete, failed, manual-review, metadata-mismatch, methodology, or supplementary files with diagnostics, combine entries into one Markdown corpus for LLM calls with explicit paper boundaries, build role-specific combined context files, regenerate clean/context artifacts, record retry-engine attempts, and convert canonical/legacy paper records into Markdown metadata plus abstract/notes/ontology-relevant sections.
- `backend/app/literature/quality.py` validates literature metadata against detected titles and DOI values, classifies document role, detects incomplete extractions from page/word/section/reference metrics, writes raw/clean/context/report/blocked artifacts, produces structured LLM-context Markdown, reports extractor availability, and centralizes automatic-extraction inclusion rules.
- `backend/app/literature/cleanup.py`, `diagnostics.py`, and `literature_types.py` implement the Phase 2 cleanup and quality support layer: named boilerplate rules, cleanup rule counts/examples, reference separation, page-marker-aware diagnostics, duplicate-text warnings, scanned/low-text indicators, and final usability statuses.
- `backend/app/literature/canonical.py` wraps the working importer with staged and curated repositories. Identified items default to `publisher_api_required`, try structured provider adapters first, classify `literature_type` for articles/preprints/books/chapters/conference papers/reports, run metadata/Markdown quality checks, and create blocked metadata-only staged entries with source reports when structured full text is unavailable. `pdf_fallback_allowed` and `pdf_only` are explicit alternatives; fallback provenance records the selected mode, XML/PDF use, authorization, errors, and artifact paths. Successful Elsevier XML and XML-derived Markdown remain authoritative. Manual Markdown upload/validation writes `manual.md`/canonical staged Markdown only after validation passes; invalid Markdown remains blocked from promotion/curation. Import writes project-local `sources/`, `markdown`, and `metadata` outputs plus repository-relative artifact/provenance manifests; isolated publisher diagnostics write only `api_tests/`. Promotion writes reviewed artifacts under `curated/`, records staged traceability/ownership, and rebuilds downstream combined Markdown from curated entries only. Its bounded cleanup removes unpromoted manifests and untracked legacy artifacts only from known OCA-managed literature folders while protecting curated, promoted, and external files. `backend/app/literature/pipeline.py` remains a compatibility wrapper and obeys the same extraction mode.
- `backend/app/literature/publisher_xml.py` defines normalized `ArticleIdentifier` collection in PII → DOI → ISSN → ISBN → URL → PMID → PMCID order. Elsevier retrieval explicitly supports PII/DOI only: recoverable identifier-specific failures advance to the next supported identifier, unsupported kinds are recorded as skipped, and configuration/authentication/permission/quota/network/server failures stop. Requests use `Accept: text/xml`, `X-ELS-APIKey`, and optional `X-ELS-Insttoken` headers; credentials never enter query strings or logs. The module parses Elsevier XML with the Python standard library and converts structured article content, including root/body sections, appendices, captions, tables, and references, to Markdown.
- `backend/app/literature/providers/` defines the provider interface and initial adapters. `elsevier_provider.py` delegates to the existing Elsevier XML workflow. `arxiv_provider.py` is the source/e-print extension point. `crossref_provider.py` resolves DOI metadata and records Crossref links. `acs_provider.py` handles ACS DOI metadata/link inspection and marks Crossref PDF links as unavailable for automatic parsing. PMC, PubMed, Unpaywall, generic HTML, and PDF providers are scaffolded as explicit status adapters for later structured integrations; the PDF provider stays disabled unless a user-authorized fallback mode is selected.
- Section detection handles numbered headings, numbered subsections, canonical scientific headings, short standalone headings, front matter before the first heading, deterministic heading normalization, and section page ranges. Canonical output uses `content.sections`; page-level text is omitted by default unless `--include-pages` is used.
- `/api/zotero/entries` starts from Zotero rows in SQLite for stable source IDs, but merges each row with the matching Markdown repository entry when available. The frontend details panel displays raw Markdown, clean Markdown, LLM-context Markdown, the corresponding Markdown file path, and readable review metadata.
- `PATCH /api/literature/repository/review` updates curator-controlled repository front matter such as `include_in_llm_extraction`, `metadata_match_status`, `document_role`, `requires_manual_review`, and `state`.
- `GET /api/literature/doctor`, `GET /api/literature/repository/report`, `POST /api/literature/context/build`, `POST /api/literature/repository/retry-extraction`, `POST /api/literature/repository/regenerate-clean`, and `POST /api/literature/repository/regenerate-context` expose extractor availability, quality summaries, role-specific combined context generation, retry metadata, and artifact regeneration to the browser.
- Browser Zotero sync persists Zotero identifier metadata in `literature_sources.identifiers_json`; the publisher lookup helper normalizes it before use. With an active project, sync attempts publisher XML import per source. In the default mode it reports actionable failures and never scans local PDF storage. Browser and CLI imports may reach the PDF pipeline only when `pdf_fallback_allowed`, `pdf_only`, or the one-shot fallback flag is explicit.
- `POST /api/config/zotero` stores empty optional Zotero fields as empty runtime values so clearing the API key or collection key in the browser actually removes previously saved values while still returning masked JSON status.
- `POST /api/literature/repository/reset` requires explicit confirmation and resets the configured literature base directory, including copied PDFs, generated Markdown, per-paper Markdown, combined Markdown, and stale sidecars, then clears stored literature rows/extraction state. The reset refuses root-like targets and does not follow symlinks. The Literature page exposes this action with a browser confirmation prompt, and `oca literature reset-repository --yes` exposes the same reset path from the CLI.
- Two-stage routes add `GET/PATCH /api/literature/staged/{id}`, `POST /api/literature/staged/{id}/manual-markdown`, staged promote/reject actions, `GET/PATCH /api/literature/curated/{id}`, strict/default `POST /api/literature/import`, `GET /api/literature/import-diagnostics`, isolated `POST /api/literature/test-publisher-api`, dry-run/confirmed `POST /api/literature/cleanup-staged`, `GET /api/project-tags`, `POST /api/literature/{item_id}/tags`, and tag filtering through literature list endpoints. The canonical literature list endpoint excludes promoted/accepted/curated staged metadata from `staged_entries`, and project-tag endpoints normalize legacy aliases to each project's single canonical tag before display/filtering. Cleanup aggregates the active project repository and a distinct configured legacy global literature repository. `/api/config/status` always includes a non-null publisher object with empty/default Elsevier fields, additional masked provider settings, and the extraction mode; `/api/config/publisher` merges optional flat provider settings through `AppSetting`, permits empty secrets, preserves unrelated keys, and creates/updates a masked, activatable publisher entry under `/api/config/saved`. `/api/config/publisher/test` returns masked configured/missing provider status without live network validation. Environment values take precedence. Settings and the CLI expose `publisher_api_required`, `pdf_fallback_allowed`, and `pdf_only`; `oca literature test-api` exercises retrieval/parsing independently from staging and PDFs.
- `ontology_curation_assistant/__main__.py` exposes the same Typer CLI through `python -m ontology_curation_assistant`.

## Zotero Local Markdown Export

- `zotero_lit_md/cli.py` implements the argparse CLI with first-class commands for `pdf-to-md`, `folder-to-md`, `extract-zotero`, `extract-storage`, `trace-item`, and `doctor`. `pdf-to-md` and `folder-to-md` are API-free local PDF-to-Markdown commands; `extract-zotero` selects parent items by collection name/key, explicit item keys, or all items with PDF attachments; `extract-storage` bypasses the API and processes all PDFs or query-ranked PDFs from a Zotero storage folder; `trace-item` writes `zotero_lit_md_trace.json` with the parent-to-child-to-storage-to-PDF chain. Legacy compatibility commands remain available for `extract-one`, `scan-storage`, `extract-one-storage-key`, `extract-storage-folder`, `from-folder`, and top-level selection flags.
- `zotero_lit_md/local_pdf.py` is the API-free PDF foundation. It defines `ExtractedPage` and `ExtractedPdf`, discovers PDFs recursively or non-recursively, extracts page text with PyMuPDF, lightly cleans repeated blank lines/page numbers/headers/footers/hyphenated line breaks, converts detected scientific headings and figure/table captions to Markdown, builds local retrieval chunks, handles output filename collisions, and writes the required LLM-ready Markdown structure.
- `zotero_lit_md/zotero_client.py` implements `ZoteroLocalClient` against `http://127.0.0.1:23119/api/`, including connection testing against `users/0/items?limit=1&format=json`, item/collection/saved-search retrieval, child attachment lookup, PDF attachment filtering, linked-file path handling, and filesystem-first stored PDF discovery through `find_pdfs_for_attachment_key(storage_path, attachment_key, metadata)`. For stored attachments, Zotero API `path`, `filename`, `contentType`, and `title` fields are treated only as relevance hints; the resolver recursively scans `{storage_path}/{attachmentKey}/` for `.pdf`/`.PDF` files and sorts matches by metadata filename, `storage:` hint, title words, then alphabetically. `find_pdf_for_attachment_key(zotero_data_dir, ...)` remains as a backward-compatible wrapper.
- `zotero_lit_md/pdf_extractor.py` uses PyMuPDF first and `pypdf` as fallback. It extracts page-level text, applies a simple two-column reading-order heuristic for text blocks, retains page numbers internally, and marks encrypted, missing, or incomplete text in diagnostics rather than inventing content.
- `zotero_lit_md/text_cleaning.py` removes repeated running headers/footers and page numbers, fixes safe hyphenated line breaks, normalizes whitespace, detects section headings, and builds deterministic filesystem-safe filenames.
- `zotero_lit_md/markdown_writer.py` renders the required Markdown structure with parent item key, attachment key, PDF path, extraction diagnostics including extracted character count, abstract, keywords, concept-map scaffold, full paper body, retrieval chunks, claim units, optional JSON sidecars, optional combined corpus, and failure reports.
- `zotero_lit_md/chunking.py` and `zotero_lit_md/diagnostics.py` create page-aware retrieval chunks and conservative claim units only from extracted paper text.

## Existing Ontology Flow

- `backend/app/ontology/local.py` scans configured ontology folders and indexes supported files.
- RDF/OWL/Turtle files are parsed with `rdflib`.
- OBO and ROBOT/template TSV files are parsed with simple local readers.
- Indexed term payloads include term ID/IRI, label, definition, synonyms, parents, and source file.
- The browser Existing Ontology page calls `/api/ontology/status` for active-project-scoped source status and then project-scoped term/search/tree endpoints. The legacy scan/select/index endpoints remain available for compatibility, but the browser page no longer uses them as its source of truth.
- Ontology status reports no-active-project, missing-project-ontology, and selected-file parse errors, while term and search endpoints return controlled HTTP 400 responses if the selected ontology file cannot be parsed.
- `/api/ontology/graph` maps indexed terms to graph nodes and parent/subclass edges.
- `/api/ontology/tree` maps indexed terms to tree-ready data: flat `nodes` with labels, definitions, synonyms, source metadata, parent/child IDs and relations; `hierarchy_edges` marked `edgeType: "hierarchy"` and `relation: "is_a"`; non-hierarchical `relation_edges` marked `edgeType: "semantic"`; root IDs; nested visible roots for compatibility; source metadata; parse time; and warnings. The browser ontology page uses this payload as the default visualization instead of the older circular graph.
- `/api/ontology/relation-types` returns the backend-owned relation catalogue used by graph-assisted candidate review. The static catalogue lives in `backend/app/ontology/relations.py` and includes relation labels, ontology IDs where available, inverse labels, descriptions, and simple source/target expectations.
- `backend/app/static/app.js` renders the ontology payload with `deriveVisibleOntologyTree()`, `layoutOntologyTree()`, and `renderOntologyTreeSvg()`. The frontend stores the full payload in `state.ontologyTree`, derives a smaller visible section from the root filter, selected/focused node, expanded/collapsed state, and depth control, then computes node positions only from visible `is_a` hierarchy edges. Node clicks set `state.selectedOntologyNodeId`, apply visible selected/context/dimmed styles, and update `showOntologyNodeDetails()`. Semantic relations are drawn afterward as dashed side links for visible or focused nodes, with toggles for semantic edges, relation labels, and node labels.
- The ontology browser controls in `backend/app/static/index.html` support class search/jump, focus on selected class, reset overview, depth selection, expand/collapse, zoom in/out, pan, fit, and center selected node. Node clicks update `state.selectedOntologyNodeId` and the detail panel.
- `/api/meta-ontology/graph` returns the curation meta-model for compatibility, but the dashboard now uses the project hierarchy tree instead of the meta-ontology graph.

## Ontology Suggestions Flow

- `backend/app/ontology_suggestions.py` stores reusable prompt templates as one Markdown file per template under `data/ontology_suggestions/prompts/`, with required YAML front matter and Markdown prompt bodies. It bootstraps conservative term, relation, definition-improvement, duplicate-check, evidence-mapping, and competency-question templates when missing, and migrates legacy JSON prompt files by creating Markdown equivalents.
- `/api/ontology-suggestions/status` reads the selected project, project-tag-linked curated/uncurated literature, and the project configured ontology path without changing literature metadata or project tags.
- `/api/ontology-suggestions/preview` assembles the final prompt from explicit literature scope, ontology context mode, and a temporary prompt copy. It reports approximate input tokens, configured max output tokens, optional locally configured cost estimates, and budget warnings.
- `/api/ontology-suggestions/test` and `/api/ontology-suggestions/test-api` remain provider connectivity checks with no real literature or ontology context. `/api/ontology-suggestions/test-pipeline` performs the main LLM pipeline test with the selected project, one selected Markdown literature item, selected ontology context, and selected prompt template, then writes diagnostics/log files without creating review suggestions. Diagnostics distinguish configuration, request, HTTP, JSON parse, and schema validation failures, and record whether JSON was parsed directly or recovered from a whole-response fenced JSON/code block.
- `/api/ontology-suggestions/run` reuses the same selected project/literature/ontology/prompt assembly path as the LLM pipeline test, validates strict ontology-suggestion JSON, stores sanitized run metadata/raw response separately from the literature pipeline under `data/ontology_suggestions/runs`, and persists reviewable `Suggestion` rows linked to a `CurationRun` with `prompt_strategy="ontology_suggestions"`.
- Accepted or edited ontology suggestions create normal `CandidateTermRecord` rows for the existing human curation queue. Rejected, duplicate, unsupported, and discussion statuses remain review decisions only. No LLM output writes ontology files, ODK templates, GitHub state, or project tags.
- `backend/app/llm/clients.py` now carries optional provider usage metadata on `LlmTextResult` so actual token usage can be logged when a provider returns it. OpenAI-compatible responses read `usage` from the chat completion payload.

## Candidate Flow

- `backend/app/extraction/service.py` persists validated candidate payloads.
- `backend/app/llm/presets.py` stores editable provider presets for Gemini, OpenAI, Anthropic, and custom OpenAI-compatible endpoints, plus provider alias normalization so UI labels such as `Gemini API`, `Google Gemini`, and `google-ai` resolve to canonical keys.
- `backend/app/llm/clients.py` defines the provider-neutral LLM abstraction. It includes Gemini, OpenAI, Anthropic, and custom OpenAI-compatible clients, secret-safe API key resolution through stored keys or environment variables, approximate input-size estimation, provider-key diagnostics, and a low-token connection test helper.
- `backend/app/llm/service.py` provides deterministic mock extraction and optional provider-neutral LLM candidate extraction.
- `backend/app/llm/curation.py` validates the saved curation prompt, selected `.obo` ontology file, current `combined_literature.md`, and LLM provider/API config; assembles the final LLM request in deterministic sections; chunks oversized literature according to `OCA_LLM_CONTEXT_CHAR_LIMIT`; calls the configured provider abstraction; validates JSON responses; reports approximate input character/token count; and writes sanitized request plus response/raw-response traces under `literature/curation_runs/`.
- `backend/app/llm/ontology_suggestions.py` builds a complete literature export from the canonical Markdown repository, creates a traceable ontology-suggestion prompt, validates the required `suggestions` JSON shape, supports a no-credentials dry run through `oca llm-ontology-suggestions`, and uses the provider abstraction for non-dry-run calls.
- Browser candidate extraction uses all valid and usable `ready_for_llm` Markdown literature files from the configured repository when no source is explicitly supplied. Empty repositories return a controlled import-literature-first error, malformed or unusable Markdown files are skipped with warnings when valid files remain, and `dry_run: true` reports included/excluded repository files plus estimated context size without extraction.
- Candidate records store curator edits, evidence, selected OLS match, selected local ontology match, lookup statuses, graph-assisted review proposals in `graph_review_json`, and curator decision.
- The default `/api/candidates` active queue returns only `new`, `in_review`, `needs_more_evidence`, and `deferred` records, so approved and rejected candidates are removed from the curation list after review.
- Candidate records also store permanent rejection timestamp and optional rejection reason.
- Active candidate listing excludes permanently rejected candidates by default.
- Temporary rejection is browser-session-only and hides the visible queue without changing persistent candidate state.
- OLS matching is implemented in `backend/app/ontology/ols.py`.
- Local PPO matching uses `backend/app/ontology/local.py`.
- Neither OLS nor local matches are auto-selected; the UI defaults to `Nothing selected`.
- Tree rendering is defensive: empty hierarchy data displays an empty state, the default overview is shallow and capped to a small top-level section, branches can be collapsed or expanded, focus mode shows one ontology neighborhood at a time, semantic side links are optional, node/relation labels can be toggled, and node selection shows details without using the older circular ontology graph as the default.
- The Candidate Curation page includes a graph-assisted ontology context panel. Graph actions set the active candidate's proposed parent, relation source, relation target, duplicate target, comparison note, and proposed relation review data. These actions update the candidate form and `graph_review_json`; ontology files are changed only through the existing accepted-candidate export/ODK workflow.

## Export Flow

- `backend/app/odk/integration.py` writes approved candidates as ROBOT-template TSV or simple candidate TSV.
- Exports include candidate label, definition, evidence, source document ID, selected OLS match, selected local ontology match, curator decision, mappings, and proposed parent/context.
- `backend/app/odk/integration.py` also validates the configured `OCA_PPO_ODK_ONTOLOGY_PATH` and can stage generated ontology artifacts beneath that directory.
- `backend/app/odk/workflow.py` is the safe implementation orchestrator. It selects only `approved` and `approved_with_edits` candidates, validates and audits an optional ontology-suggestion trace file, writes the configured ROBOT template, marks accepted candidates through `implemented`, `validated`, and `uploaded` states, runs the configured validation command, blocks upload on validation failure, and defaults to dry-run mode.
- `backend/app/github_export.py` saves generated ontology artifacts to GitHub through the contents API. It reads `GITHUB_TOKEN`, `GITHUB_REPOSITORY`, `GITHUB_BRANCH`, and optional `GITHUB_BASE_PATH`, supports create/update semantics, and returns commit metadata or clear configuration/API errors.
- `POST /api/odk/workflow` exposes the orchestrator to the browser/API. Non-dry-run calls require `production=true`. The CLI exposes the same path through `oca odk-apply-approved`, with `--no-dry-run --production` required for real validation/upload.
- `backend/app/audit/logging.py` appends secret-redacted JSONL audit events for candidate proposal/review/decision changes. The ODK workflow writes implementation, validation, stop, and upload events to the configured audit log.
- Project-scoped ODK support currently adds safe validation/logging and accepted-suggestion TSV export through `backend/app/projects.py`. `oca ontology build` and `oca ontology test` intentionally log pending manual operations rather than executing external commands until per-project safe execution and backup/clean-git checks are configured.

## Persistence

- SQLAlchemy models live in `backend/app/models/db.py`.
- Runtime schema creation and small SQLite-compatible schema additions live in `backend/app/db/session.py`.
- The project does not yet use Alembic migrations.
- New project tables are created by `Base.metadata.create_all()`. Nullable project columns are added to existing tables through `ensure_runtime_schema()`.
